# PRD：美股投研 Agent（AlphaDesk）

版本 v0.1 · 2026-11-05 · 状态：原型

*English summary: A research copilot for retail investors and licensed advisors covering five Nasdaq names. It answers filing questions with citations, runs multi-tool analysis (price, financials, portfolio risk), and drafts simulated orders that only a human can confirm. Success is measured by task success, tool-selection accuracy, citation accuracy, confirmation compliance, latency and cost.*

## 1. 问题

个人投资者和券商投顾在研究美股时有三类重复劳动：

1. 查财报原文。10-K 动辄 30 万字符，找一句客户集中度或关税影响的披露要翻很久。通用聊天机器人能回答，但经常给不出出处，数字也可能是旧的或编的。
2. 拼数据。一个"我的组合风险大不大"的问题，需要行情、持仓、波动率、回撤、beta，分散在不同工具里。
3. 从分析到下单的衔接。Agent 能调用交易接口之后，误操作和越权成为主要风险。投顾场景还有适当性和合规要求。

我在券商做投资顾问三年，上面三件事每天都在做。这个原型想验证：用工具调用 + 带引用的检索 + 人工确认闸门，能否让 Agent 在这类任务上可用，并且可以被量化评估。

## 2. 目标用户

| 用户 | 典型需求 | 关注点 |
|---|---|---|
| 个人投资者（有美股账户，持仓 3 到 10 只） | 快速了解公司基本面、看自己组合风险 | 回答准确、有出处、不被诱导重仓 |
| 券商投顾 / 理财经理 | 给客户准备材料，回答客户提问 | 每个数字能追溯到原文；合规话术；不能代客操作 |
| 投顾团队负责人 / 合规 | 审查 AI 输出 | 可回放的轨迹、违规请求的拦截率 |

## 3. 核心场景

1. **财报问答带引用**："英伟达 2026 财年最大客户占比多少？"Agent 检索 10-K，回答 22%，并标注 `[NVDA-10K-7-016]`。用户点开 chunk 可以看到原文和 SEC 链接。
2. **多工具分析**："我持有 NVDA 60%、TSLA 40%，风险如何？"Agent 调用 `portfolio_risk`，给出年化波动率、最大回撤、beta、集中度提示。
3. **记忆**：用户说过一次持仓和风险偏好后，Agent 写入用户画像，下次"看看我的组合"不用重复输入。
4. **下单需确认**："帮我买 10 股 AAPL。"Agent 生成模拟订单，系统弹出确认，用户输入 yes 才生效。用户说"不用问我"也照样需要确认。
5. **违规请求拒答**："保证收益的股票""我有未公开的消息"，Agent 拒绝并说明原因，不调用下单工具。

## 4. 范围

**本期做：**
- 5 家纳斯达克公司（NVDA、MSFT、AAPL、TSLA、AMZN），QQQ 作为基准
- 7 个工具，同一套实现同时提供给 MCP 客户端和自研 Agent
- 最新一期 10-K 和 10-Q 的检索与引用
- 模拟下单与人工确认
- 三层评测：工具单测、检索评测、Agent 任务评测

**本期不做（non-goals）：**
- 不接入任何真实交易通道，也不保存券商账户凭证
- 不提供实时行情（使用日线收盘价，并在结果中注明）
- 不做个性化投资建议和收益预测
- 不做 A 股和港股（数据源和披露格式不同，放到路线图）
- 不做向量检索。先用 BM25 建立可解释的基线，再决定 embedding 是否值得引入成本

## 6. 风险与合规设计

### 6.1 为什么下单必须人工确认

- **责任归属**：下单是不可撤销的资金操作。按券商业务规范，交易指令应由客户本人发出，投顾不能代客操作，AI 更不能。
- **模型不可靠**：模型可能误解数量（"买 10 手"还是"10 股"）、搞错代码，或被提示注入诱导下单。
- **用户的话不等于授权**："不用问我直接买"不能作为跳过确认的依据，评测集里专门有这类任务（A22）。

### 6.2 实现方式

1. `draft_order` 只生成 `PENDING_CONFIRMATION` 状态的模拟订单，同时生成一次性确认 token，10 分钟过期。
2. token 只保存在本地，不返回给模型。模型没有任何工具可以确认订单。
3. 自研 Agent 中，确认由 `confirm_fn` 完成（CLI 中是终端输入 yes）。MCP 场景下，确认需要用户在本地运行 `python -m finagent.orders confirm <id>` 并手动输入订单号。
4. 额外校验：代码白名单、数量为正整数、限价单必须有价格、单笔名义金额上限 10 万美元。
5. 即使确认，订单状态也只是 `SIMULATED_CONFIRMED`，代码中没有任何交易接口。

### 6.3 其他合规措施

- **引用约束**：系统提示要求财报相关回答必须标注 `[chunk_id]`，评测会检查引用是否真实来自本次检索。
- **违规请求规则**：关键词规则识别"保证收益""内幕消息""拉抬股价"等请求，命中后在上下文中加入合规提示，并在轨迹中打标签，便于合规抽查。规则是软提示，最终是否拒答由模型决定，评测衡量实际效果。
- **数据时效**：行情结果注明"日线收盘价，非实时"，每个结果带 `as_of` 或 `fetched_at`。
- **可回放**：每次运行的步骤、参数、输出预览、token 都写入 JSONL，合规可以逐条回放。
- **免责**：系统提示要求说明不构成投资建议。

### 6.4 已知风险

| 风险 | 影响 | 当前缓解 | 后续 |
|---|---|---|---|
| 检索漏召回（约 16% 的题 top-5 未命中） | 回答缺依据或答错 | 要求引用，无依据时应说明 | 混合检索、查询改写 |
| 关键词规则漏判变体说法 | 违规请求未被标记 | 系统提示兜底 | 加分类模型 |
| 财报表格转文本后结构丢失 | 数字类问题检索差 | 结构化数字走 XBRL 工具 | 表格单独解析 |
| 模型编造 chunk_id | 虚假引用 | 评测检查 grounded | 生成后自动校验并删除无效引用 |

## 7. 成本模型

单任务成本 = Σ（每次模型调用的输入 tokens × 输入单价 + 输出 tokens × 输出单价）。

影响输入 tokens 的主要因素（实测字符数）：
- 工具定义（8 个工具的 JSON schema）：3,708 字符，每次调用都要带
- 系统提示：455 字符
- 一次 `search_filings`（k=5）返回：约 6,600 字符，是最大的单项
- `portfolio_risk` 返回约 490 字符，30 日 `get_price_history` 约 2,000 字符

下面是**假设性估算**，用于决定优化方向，实际值以评测记录的 token 为准：

假设一个财报问答任务调用模型 2 次，平均每次输入 5,000 tokens、输出 300 tokens。按 DeepSeek 官方价格（deepseek-flash 高峰时段：输入 0.30 美元/百万 tokens，输出 1.20 美元/百万 tokens），单任务约 2 ×（5,000 × 0.30 + 300 × 1.20）/ 1,000,000 = 0.0037 美元。

降本手段，按优先级：
1. 检索结果截断（当前每段 900 字符）和 k 值调优，这是最大的输入来源
2. 历史消息中的工具结果做摘要，而不是原样保留
3. 简单问题走更便宜的模型，复杂分析再用大模型
4. 利用服务商的上下文缓存（工具定义和系统提示是固定前缀）
